# 1. 概要

## 1.1 目的

本ゲームは、修士研究「生成AIを用いた自由入力機能の導入が、プレイヤーの対話行動およびゲーム体験に与える影響」のために開発する研究用RPGプロトタイプである。

プレイヤーが小規模な街を探索し、NPCとの会話からクエスト達成に必要な情報を収集するゲームとする。

本研究では、NPCとの対話方式の違いがプレイヤーのゲーム体験に与える影響を比較する。

## 1.2 実験条件（設計意図）

基本的に以下の2条件を想定する。

### 条件A：選択肢型NPC対話

NPCとの会話において、ゲーム側があらかじめ用意した選択肢からプレイヤーが発言を選択する。

### 条件B：生成AIを利用したNPC対話

基本的な会話構造は選択肢型と同様とするが、プレイヤーが自由入力によってNPCに質問できる。

自由入力を選択した場合、プレイヤーが文章を入力し、生成AIによってNPCの返答を生成する。

生成AIにはNPCごとの役割・性格・知識・ゲーム内設定などをシステムプロンプトとして与える。

> **実装メモ**：条件の切り替えは、クエストやNPCに紐付けず「参加者が今どちらの条件で遊んでいるか」という全体設定として持たせる。同じNPC・同じクエストのままでも、条件Aのときは選択肢のみ、条件Bのときは同じ場面に「入力する」という選択肢が追加される、という形にする（詳細は19章・20章参照）。現状のCSVの`allowInput`列（ノード単位の設定）だけでは、クエストと条件を独立させる設計を表現できないため、別途実装が必要。

# 5. NPC

## 5.1 NPC基本仕様（実装準拠）

`NPCDialogue`コンポーネントが保持するのは以下のみ。

* `npcId`（string）……NPCの識別名。**会話ウィンドウの表示名としてもそのまま使われる**（`nameText.text = currentNPC.npcId`）。個別の「表示名」フィールドは存在しない
* `csvFileName`（string）……`Resources/dialogue/`配下の会話CSVファイル名
* `promptData`（`PromptData`）……AI用システムプロンプト（1本の文字列）
* `allowUserInput`（bool）……**現状どこからも参照されていない未使用フィールド**。自由入力の可否は代わりにCSV側の`allowInput`列で制御される

役割・性格・背景設定・伝えられる情報・クエスト関連情報・会話ルールなどは、個別フィールドとしては存在せず、**すべて`PromptData.systemPrompt`のテキスト内に人間が手書きで埋め込む**運用になっている（9.3章参照）。

NPCごとに `NPCDialogue` のInspector値・CSV・PromptDataアセットを差し替えることで異なる設定を持たせる。

# 7. 選択肢型対話（実装準拠）

## 7.1 基本仕様

CSVの1ノードにつき、選択肢は最大で以下の3つまで（DialogueManager.ShowChoicesFromNode）：

1. `choiceA`（テキストが空でなければ表示）
2. `choiceB`（テキストが空でなければ表示）
3. 「入力する」（そのノードの`allowInput`が`1`の場合のみ、AI自由入力への導線として自動追加）

元仕様書にあった「2〜4個程度の自由記述の選択肢」という汎用的な分岐システムではなく、**分岐は1ノードにつき最大2択＋自由入力の計3択に固定**されている。「何も聞かない」のような選択肢を出したい場合は、`choiceA`または`choiceB`のテキストとしてそのまま書き、遷移先ノード（またはダイアログ終了用の`nextId = -1`ノード）を割り当てる形になる。

選択肢が1つも無いノード（`choiceA`・`choiceB`とも空、`allowInput`も0）の場合は選択肢UIは出さず、`nextIndicator`（次へ進む案内）のみ表示する。このとき状態は必ず`InDialogue`に戻す（2026-10-04修正：以前は選択肢から遷移してきた場合に`InChoice`のまま残り、Enterで前の選択肢が再実行されて`nextId`へ進めない不具合があった）。

## 7.2 選択肢操作

* 上キー：選択肢を上へ移動
* 下キー：選択肢を下へ移動
* Enter：選択肢を決定

（`HandleChoiceInput`。矢印キーの実装は元仕様書通り）

# 8. 自由入力対話（実装準拠）

## 8.1 基本仕様

生成AI条件では、CSVの`allowInput`が`1`のノードに到達すると、選択肢の一番下に「入力する」という項目が自動的に追加される。元仕様書の例のように常に`[自由入力]`という固定ラベルの選択肢が出るわけではなく、**ノードごとに出す／出さないを制御する**。

選択して決定すると `OpenInputMode()` が呼ばれ、状態が `InTyping` に遷移し `inputPanel` を表示する。このときも `dialoguePanel`（NPC名・直前の発言）は非表示にしないため、実質的に元仕様書のモックアップ（会話内容＋入力欄が同時に見える構成）と近い見た目になる。

```text
┌──────────────────────────────┐
│ NPC名                         │
│ （直前の会話内容がそのまま残る）│
├──────────────────────────────┤
│ ここに質問を入力              │
└──────────────────────────────┘

              [送信]
```

`OnClickSend()` → `SubmitTypedText()` で `ChatGPTClient.SendChatMessage` を呼び出し、返答を待つ間はプレイヤー操作不可のまま。

# 9. 生成AIシステム

## 9.1 API

OpenAI APIを使用する。`UnityWebRequest`でHTTPリクエストを送信し、NPCの返答を取得する。

Chat Completions API（`https://api.openai.com/v1/chat/completions`）を使用する。

## 9.2 AIモデル

`ChatGPTClient.cs` 内で以下のモデル名が定数として設定されている：

```csharp
private const string model = "gpt-5.6-luna";
```

> **要確認**：この名前は実在のOpenAI公開モデル名の命名規則と一致しない可能性がある。実験開始前に、実際にAPIから利用可能なモデル名かどうかを確認し、必要であれば更新すること（元仕様書21章の「研究データの再現性」に従い、確認後は実験期間中みだりに変更しない）。

## 9.3 NPCプロンプト（実装準拠）

`PromptData`はScriptableObjectで、フィールドは`systemPrompt`（`[TextArea(3,10)]` の1つの文字列）のみ。構造化されたフィールド（名前／役割／性格／背景／知っている情報…）は存在せず、**それらを含んだプロンプト全文を1つの文字列としてそのままアセットに書き込む**運用。

現在登録済みの例（`Resources/PromptData/NPC001.asset`）：

```text
あなたはRPGの村のNPCです。役職は商人です。
80文字以内の自然な日本語で返答してください。
プレイヤーの質問に対して感情を少し入れてください。
```

元仕様書にあるテンプレート（【名前】【役割】【性格】【背景】【知っている情報】【知らない情報】【クエストに関する情報】【会話ルール】…という見出し付きの構成）は、**このsystemPromptの文字列を書く際の「執筆ガイドライン」として引き続き有効**。今後NPCを追加する際もこのテンプレートに沿ってプロンプト文字列を作成するとよい。

## 9.4 クエストNPC用プロンプトテンプレート

19章のクエストに登場する情報提供NPC向けに、テンプレートを具体化する。ポイントは、**「知っている情報」＝そのNPCが持つ手がかりを、選択肢で聞かれても自由入力で聞かれても同じ内容で答えられるようにすること**。自由入力はあくまで会話を掘り下げる用途なので、手がかりの中身を変えたり、新しい手がかりを勝手に作り出したりしないよう釘を刺しておく。

```text
あなたは村に住む{{役職}}の{{名前}}です。

【役職・見た目】
{{役職（薬師／商人／貴族／平民／鍛冶屋／料理人など、実際に使う3Dモデルの役職と合わせる）}}

【性格】
{{一言で表せる人物像}}

【背景】
{{今何をしていて、なぜその手がかりを知っているのか}}

【知っている情報（聞かれたら教えてよいこと）】
{{そのNPCが持つ手がかりの内容そのもの}}

【知らない情報・話してはいけないこと】
- 自分の手がかり以外のこと（他のNPCが持つ手がかりや、クエストの答えそのもの）は知らない
- ゲームに存在しない場所・人物・アイテムを話に出さない
- クエストの正解となる手がかりの内容を変えたり、新しい手がかりを作り出さない
- 自分がAIであることには触れない

【会話のルール】
- 80文字以内の自然な日本語で答える
- {{名前}}らしい口調を保つ
- 深く聞かれた場合も、「知っている情報」と矛盾しない範囲で少し詳しく答えてよい（例：時間や様子をもう少し具体的に描写する程度の肉付け）
- 手がかりと関係ない質問には、世界観に沿った短い世間話として答える
```

**記入例（クエスト1「消えた薬草」の鍛冶屋、「時間」の手がかり担当）**

```text
あなたは村に住む鍛冶屋のガルドです。

【役職・見た目】
鍛冶屋

【性格】
無口だが親切。仕事の手を止めずに、聞かれたことには簡潔に答える。

【背景】
村の入り口のそばに工房を構えていて、薪や鉄を運ぶために入り口を毎日通っている。

【知っている情報（聞かれたら教えてよいこと）】
昨日の夕方、村の入り口のあたりで誰かが荷物をいじっているのを見た。暗くて顔や持ち物までは見えなかった。

【知らない情報・話してはいけないこと】
- 薬草そのものの行方や、荷物をいじっていたのが誰かは知らない
- ゲームに存在しない場所・人物・アイテムを話に出さない
- クエストの正解となる手がかりの内容を変えたり、新しい手がかりを作り出さない
- 自分がAIであることには触れない

【会話のルール】
- 80文字以内の自然な日本語で答える
- 無口な鍛冶屋らしく、飾らない短い言葉遣いにする
- 深く聞かれた場合も、「知っている情報」と矛盾しない範囲で少し詳しく答えてよい（例：何時ごろか、どんな様子だったか程度の肉付け）
- 手がかりと関係ない質問には、世界観に沿った短い世間話として答える
```

依頼人（薬師ジョン・村長トーマス）は手がかりを持つ側ではなく受け取る側なので、「知っている情報」の代わりに依頼内容とクエストの状況（まだ手がかりが揃っていない／揃った）を書く形になる。これは実際にNPCを実装する段階で個別に用意する。

# 10. AI対話の制約（設計意図・変更なし）

研究目的のため、生成AIがゲーム進行を破壊しないことを重視する。

* NPCの設定を逸脱しない
* 存在しないNPCを作らない
* 存在しない場所を作らない
* 存在しないアイテムを作らない
* クエストの正解情報を勝手に変更しない
* プレイヤーにゲーム外の情報を提示しない
* AI自身について説明しない
* 極端に長い回答を生成しない
* 日本語で回答する

これらは現状`systemPrompt`のテキストで運用上守らせる方針であり、コード側でのバリデーション（禁止ワード検出等）は実装されていない。

# 11. 会話状態管理（実装準拠）

状態は`GameState` enum（`Assets/Script/GameState.cs`）で定義されている。

```csharp
public enum GameState
{
    FreeMove,
    InDialogue,
    InChoice,
    InTyping,
    Ended,     // クエスト達成後の終了画面（2026-10-04追加）
    InSettings // 設定パネル表示中・時間停止（2026-10-05追加）
}
```

元仕様書の想定通りの4状態が存在する。ただし、**この状態を実際に保持・遷移させているのは`DialogueManager`の`private GameState currentState`フィールドであり、`GameManager.State`/`GameManager.SetState()`は現状呼び出されていない**（`GameManager`は`ChatGPTClient`コンポーネントを持つシングルトンとしての役割のみを果たしている）。

## FreeMove

通常の探索状態。プレイヤーの移動・カメラ操作が可能。NPCに近い場合はTalkHint類を表示。

## InDialogue

NPCとの通常会話中。プレイヤーの移動を停止。Enterで会話を進める。

## InChoice

選択肢を選択している状態。プレイヤーの移動を停止。上下キーで選択肢を移動、Enterで決定。

## InTyping

自由入力中。プレイヤーの移動を停止。`TMP_InputField`で文章を入力し、送信ボタンでAIへ送信する（`HandleTypingInput`自体はEnterで送信しないよう空実装にしてあり、IME変換中の誤送信を避けている）。

# 12. 会話終了処理（実装準拠・重要）

AIの返答表示中はプレイヤーを操作可能にしない、という元仕様書のルールは実装に反映されている。

```text
自由入力ノードに到達（allowInput=1）
 ↓
「入力する」選択 → OpenInputMode（SetTypingMode(true)でカーソル解放・移動停止）
 ↓
AIへ送信・応答待ち（この間もプレイヤー操作不可）
 ↓
ShowAIResponse：currentState = InDialogue、返答文を表示
   ※ SetTypingMode(false) はここでは呼ばれない（意図的）
 ↓
Enter
 ↓
HandleDialogueInput：currentNode（＝自由入力を開始したノード）のnextIdを見る
   NPC001の例では nextId = -1 のため CloseDialogue() が呼ばれる
 ↓
DialoguePanel等を非表示、SetTypingMode(false)でプレイヤー操作復帰
```

**注意**：AI応答後にEnterで次に進む先は、自由入力を開始した**元のノードの`nextId`**である。会話をAI応答の後にさらに分岐させたい場合は、そのノードの`nextId`が正しく次のノードを指すようにCSVを設計する必要がある（`-1`なら即終了）。

* 見た目は会話ウィンドウと同じ枠画像（`panel_rect_black-silver_03_128`）・NotoSansJP。画面中央に表示
* スライダーはマウスで操作する（開いている間はカーソルを表示し、プレイヤーの移動・カメラ操作を止める）

**開閉のルール**

* 開けるのは探索中（`FreeMove`）だけ。会話中・選択肢中・自由入力中・終了画面では`Q`を押しても開かない（自由入力の文章に「q」を打ったときに開いてしまうのを防ぐため）
* 閉じるのは`Q`のみ（`Esc`は使わない）。閉じるとプレイヤー操作が戻る
* `GameState`に`InSettings`を追加し、`DialogueManager`が他の状態と同じように管理する（開いている間は`Enter`で話しかけない）
* 開いている間はゲーム内の時間を止める（`Time.timeScale = 0`）。NPCの待機モーションなども止まる。閉じると元に戻す
* 音は止めない（BGM・SEを鳴らしたままにして、スライダーを動かしながら音量を確かめられるようにする）
* 開いていた時間はプレイ時間に含めない。Phase 8のログでは開閉時刻を記録し、時間を計るときは`Time.time`（止めている間は進まない）を使う想定

**視点感度**

* マウスで視点を回す速さの倍率。範囲0.2〜3.0、初期値1.0（今と同じ速さ）。表示は「1.0」のように小数1桁
* 購入アセットの`ThirdPersonController`・`StarterAssets.inputactions`は変更しない。`LookSensitivitySettings`（`GameManager`に付けた）が、`PlayerInput`のLookアクションの各バインディングに、元からあるプロセッサ（マウス×0.05、ゲームパッド×300など）の後ろへ`ScaleVector2(x=感度,y=感度)`を実行中だけ追加する
* 音量と同じく**保存せず、起動するたびに1.0に戻す**（参加者間で条件をそろえるため）

**初期位置に戻る**

* ゲーム開始時のプレイヤーの位置・向き（`DialogueManager.Start()`で記録）へ瞬間移動する（`DialogueManager.RespawnPlayer()`）。建物の隙間にはまって動けなくなったときなどの救済用。カメラが村の上空を横切って追いかけないよう、Cinemachineに瞬間移動を伝えている（`OnTargetObjectWarped`）
* 押すと移動してパネルを閉じ、探索に戻る。クエストの進み具合（受注・手がかり）はそのまま
* Phase 8のログでは「初期位置に戻った」回数・時刻も記録する想定

**音量の仕組み**

AudioMixerは使わず、音量を1か所で持って各音源（`AudioSource`）に掛ける。SEはプレイヤーの足音・着地音だけで、`Player/PlayerArmature/Audio/`の`Footstep_Concrete`・`Footstep_Land`（`ThirdPersonController`から`Play()`される`AudioSource`）で鳴っている。

* `AudioVolumeSettings`（新規、`GameManager`に付ける）：BGM音量・SE音量（0〜1）を保持し、変わったら通知する
* `VolumeChannel`（新規）：BGMやSEを鳴らす`AudioSource`に付け、「BGM」か「SE」かを指定する。元の音量×設定音量を自動で反映する。今はBGMが無いので、BGMを追加するときにこれを付ける
* 足音・着地音：`Footstep_Concrete`・`Footstep_Land`に`VolumeChannel`（SE）を付ける（`Robot`は音が設定されていない空の`AudioSource`なので対象外）
* 初期値はBGM・SEとも80%。**設定は保存せず、起動するたびに初期値に戻す**（前の参加者が変えた音量が次の参加者に引き継がれると、参加者間で条件がそろわなくなるため）

**実装したもの**

* スクリプト：`AudioVolumeSettings`・`VolumeChannel`・`LookSensitivitySettings`・`SettingsPanelUI`（表示とスライダー・ボタンの処理。開閉の判定は`DialogueManager.OpenSettings()`／`CloseSettings()`、初期位置は`DialogueManager.RespawnPlayer()`）
* シーン：`Canvas/SettingsPanel`（上から`HeaderText`・`BGMRow`・`SERow`・`SensitivityRow`・`TitleButton`・`RespawnButton`・`HintText`）、`SettingsPanelUI`は`Canvas`に、`AudioVolumeSettings`は`GameManager`に、`VolumeChannel`（SE）は`Footstep_Concrete`・`Footstep_Land`に付けた

**BGM（2026-10-05追加）**

* 音源：`Assets/Audio/BGM.wav`（約82秒・ステレオ）。インポート設定は読み込み方式「Streaming」・圧縮Vorbis（品質70%）にした（長い曲を最初に全部メモリへ展開しないため）
* シーンのルートに`BGM`オブジェクトを置き、`AudioSource`（ループ再生・起動時に自動再生・2D）と`VolumeChannel`（BGM）を付けた。設定パネルのBGMスライダーで音量が変わる
* 設定パネルで時間を止めている間も、終了画面でもBGMは鳴り続ける

# 16. ChatGPTClient

## 16.1 責務

`ChatGPTClient`はOpenAI APIとの通信のみを担当する。UI制御やプレイヤー操作制御は行わない（実装済み・一致）。

## 16.2 入力

```text
userText
systemPrompt
```

## 16.3 出力

```text
AIが生成したNPCの返答（string）。通信失敗・パース失敗時は"エラー"という文字列を返す
```

# 19. クエストシステム（実装済み）

## 19.1 なぜクエストが2種類必要か、かつ条件と固定で結びつけないのか

実験参加者は条件A（選択肢のみ）と条件B（選択肢＋自由入力）の両方をプレイする。同じクエストを2回体験すると2回目は答えを覚えてしまい、対話方式の違いを正しく比較できなくなる。そのため、内容は別だが難易度・構成が対応する2つのクエストを用意する。

* クエスト1：「消えた薬草」
* クエスト2：「祭りの道具探し」

ここで、クエストと条件を固定のペアにしてしまう（例：クエスト1は常に条件A、クエスト2は常に条件B）と、条件A/Bで生じた体験の違いが「対話方式の違い」によるものなのか、「たまたまクエストの内容が違うから」によるものなのか区別がつかなくなってしまう。

そこで、クエストと条件は独立させ、参加者を次の4グループに均等に振り分けてカウンターバランスを取る。

1. 条件A×クエスト1（消えた薬草） → 条件B×クエスト2（祭りの道具探し）
2. 条件A×クエスト2（祭りの道具探し） → 条件B×クエスト1（消えた薬草）
3. 条件B×クエスト1（消えた薬草） → 条件A×クエスト2（祭りの道具探し）
4. 条件B×クエスト2（祭りの道具探し） → 条件A×クエスト1（消えた薬草）

これにより、対話条件の順序・クエストの順序のどちらも参加者間でばらけ、「条件による違い」と「クエスト内容による違い」を分けて見られるようになる。そのため、以下の2つのクエストはどちらも、条件A・条件Bの**両方で**プレイされうるものとして設計する（片方の条件専用のクエストにはしない）。

重要な前提として、**クエストを達成するのに必要な4つの手がかりは、すべて選択肢だけで入手できる**ようにする。自由入力は手がかりを得るための必須ルートではなく、あくまで条件Bのプレイヤーが会話を掘り下げて楽しめる追加の選択肢という位置づけ。条件Aには自由入力自体が無いため、この前提を守らないと条件Aではクエストを達成できなくなってしまう。

NPCの見た目は、購入済みアセットに含まれる既製の村人モデル（薬師／商人／貴族／平民／鍛冶屋／料理人など）から選ぶ。子供のモデルは用意されていないため、子供という設定のキャラクターは登場させず、大人のNPCに置き換える。

## 19.2 クエスト1：「消えた薬草」

**依頼人**：薬師ジョン（見た目：薬師）

**導入**：病人のために「クスリ草」という薬草が必要なのに、届くはずの薬草が届いていない。心当たりのある人に話を聞いて、薬草のありかを突き止めてほしいと頼まれる。

**集める手がかり（4つ）**

| 手がかり | 内容 |
|---|---|
| 場所 | 村の入り口 |
| 時間 | 昨日の夕方 |
| 人物 | 旅の行商人 |
| 特徴 | 赤い布に包まれた束 |

**話を聞く相手（3人）**

* 村人（見た目：平民）：「場所」の手がかりを知っている
* 鍛冶屋：入り口のそばの工房で仕事をしていて、「時間」の手がかりを知っている
* 料理人：村外でよく薬草や食材を採ってくることが多く、「人物」と「特徴」の手がかりを知っている

3人とも、手がかりそのものは選択肢のやり取りだけで得られる。条件Bで遊んでいる場合は、同じ場面で自由入力によってさらに深く質問し、会話を掘り下げることもできる（あくまで任意で、手がかりの入手には影響しない）。

**クエストの流れ**：プレイヤーは3人から話を聞いて回り、4つの手がかりがすべて揃った状態で薬師ジョンに報告するとクエスト達成となる。手がかりが足りないまま報告に行っても、ジョンは「まだ何か手がかりが足りなさそうだ」と返すだけで、達成にはならない。

## 19.3 クエスト2：「祭りの道具探し」

**依頼人**：村長トーマス（見た目：貴族）

**導入**：来週の収穫祭で使う灯篭が見当たらない。当時、準備を手伝ってくれた人を探していて、プレイヤーに心当たりを聞いて回ってほしいと頼む。

**集める手がかり（4つ）**

| 手がかり | 内容 |
|---|---|
| 場所 | 村の外にある倉庫 |
| 時間 | 3日前（準備を始めた日） |
| 人物 | 手伝っていた村の若者たち |
| 特徴 | 古い木箱に入っている |

**話を聞く相手（3人）**

* 商人：「場所」と「人物」の手がかりを知っている
* 村人（見た目：平民）：祭りの準備を手伝っていて、「時間」の手がかりを知っている
* 鍛冶屋：灯篭の金具を直したことがあり、「特徴」の手がかりを知っている

クエスト1と同様、手がかりは選択肢だけで揃う。条件Bで遊んでいる場合は自由入力でさらに聞き込めるが、それは任意の掘り下げであり、手がかりの入手条件ではない。

**クエストの流れ**：クエスト1と同様、4つの手がかりをすべて集めた状態で村長トーマスに報告するとクエスト達成となる。

## 19.4 2つのクエストを揃えている点

実験条件（選択肢のみ／選択肢＋自由入力）以外の差が出ないよう、以下を意図的に対応させている。

* 依頼人1人＋情報提供NPC3人という構成
* 集める手がかりのカテゴリ（場所・時間・人物・特徴）が4つ
* 物語のトーン（誰かが困っている軽い探し物で、深刻な事件性はない）
* 1人のNPCだけでは手がかりが揃わず、複数人に話しかけないと依頼を達成できない難易度
* 対話条件（選択肢のみ／選択肢＋自由入力）はクエスト側に固定せず、どちらのクエストでも同じように切り替わる（19.1章のカウンターバランス参照）
* 手がかりの入手は選択肢だけで完結し、自由入力は必須ではない（条件Aでもクエストを達成できることが大前提）

## 19.5 進行の目安

プレイヤーは常に「今どの手がかりが揃っていて、何が足りないか」を確認できるようにする。例えばクエスト1（消えた薬草）なら次のようなチェックリストが埋まっていくイメージ。

```text
消えた薬草
□ 場所（村の入り口）
□ 時間（昨日の夕方）
□ 人物（旅の行商人）
□ 特徴（赤い布に包まれた束）
```

4つすべてが埋まった状態で依頼人に話しかけると達成となる。手がかりを集める順番はプレイヤーの自由で、NPCに話しかける順序に制約は設けない。

### 19.7.1 会話の共通ルール

全NPC・両クエストで同じ型にそろえる（20.1の「条件以外の差を小さくする」ため）。

| 場面 | 型 |
|---|---|
| 依頼人・受注前（`0`〜） | 事情説明 → 「引き受ける／今は無理」。**ここで自由入力可**（依頼内容を詳しく聞ける） |

## 20.2 / 20.3 AI条件・非AI条件

* AI条件：選択肢＋自由入力
* 非AI条件：事前に用意した選択肢のみ

> **実装メモ**：19章の設計（クエストと条件を独立させ2×2でカウンターバランスを取る）により、条件の切り替えはクエストやNPCに紐付けず、「参加者が今どちらの条件で遊んでいるか」という全体設定として持たせる必要がある。同一NPC・同一クエストのままでも、条件Aでは選択肢のみ、条件Bでは同じ場面に「入力する」という選択肢が追加される、という形にする。この変更は元仕様書25.3項の「研究仕様の変更」に該当するため、実装前に影響範囲を説明すること。

# 22. エラー処理

AI API通信に失敗した場合、`ChatGPTClient.SendChatMessage`は例外を投げず`"エラー"`という文字列を返す（`Debug.LogError`でコンソールにも出力）。これは`DialogueManager.ShowAIResponse`にそのまま渡され、NPCの発言として画面に表示される（＝ゲームは停止しない）。

ただし、元仕様書が想定する「通信エラーが発生しました。もう一度送信してください。」といったユーザー向けの専用エラーメッセージや、**エラー内容自体をログとして記録する仕組みは未実装**（17章のログ未実装と合わせて対応が必要）。

# 26. 現在のUnity実装方針

Unityバージョン（実測・一致）：

```text
Unity 6000.4.2f1
```

使用中の主要パッケージ（`Packages/manifest.json`で確認済み）：

* Unity Input System 1.19.0（`Keyboard.current`ベースの直接ポーリングで使用）
* Starter Assets Third Person Character Controller
* Cinemachine 3.1.7
* Universal Render Pipeline 17.4.0
* TextMeshPro
* UnityWebRequest（OpenAI API通信）
* OpenAI API（Chat Completions、モデル名は9.2章参照・要確認）

メインシーンは `Assets/MainScene.unity`（元仕様書は`Assets/Scenes/`配下を想定していたが、実際は`Assets`直下）。

**空・環境光（2026-10-05）**

* 空：Asset Storeの無料素材「Simple Sky - Cartoon assets」（`Assets/PurchasedAssets/SimpleSky/`）。スカイボックスではなく、シーンのルートに置いた`Sky`オブジェクトの中に、空のドーム（`SkyDome`プレハブ、村の中心(11, 0, 128)・スケール1.3・半径約430m）とローポリの雲12個（`Clouds`、高さ55〜95m・村から140〜280m）を置いている。どれも影を落とさない設定
* 時間帯はマテリアルのUVオフセット（x）で決まる（0.1付近で地平線が黄色がかり夕方寄り、0.2で夕方、0.3以降で夜）。素材の`SimpleSky.mat`は直接いじらず、コピーした`Assets/Material/SimpleSky_Day.mat`（オフセット**−0.05**＝一番明るい昼の青空）をドームと雲に割り当てている（`PurchasedAssets`側の変更はGitHubに残らないため）。ドームに含まれる月（`Moon`）と星（`Stars`）は昼に合わないので非表示にした（太陽`Sun`は表示）
* 太陽（`Directional Light`）の色温度は6500K（昼の白い光）。もとは5000Kで光が黄色っぽく、夕方のように見えていた
* ドームはカメラの描画距離（500m）の内側に収まる大きさにしてある。ドームを大きくしたり、カメラのFar Clipを小さくしたりすると空が消えるので注意
* スカイボックスは使わない（`RenderSettings.skybox`なし）。環境光は3色指定（Ambient Source: Gradient／Trilight：空 RGB(140,184,242)・地平線 RGB(199,209,219)・地面 RGB(107,115,92)）。焼き込みライティングは使わない設定（`Assets/Settings/MainSceneLighting.lighting`：Baked GI・Realtime GIともオフ）
* `PurchasedAssets`はGitHubに含まれないので、**別のPCで開くときはAsset Storeから「Simple Sky - Cartoon assets」をインポートし、`Assets/PurchasedAssets/SimpleSky/`に置くこと**（置かないと空が表示されない）
* 最初に試した「Skybox Series Free」（374MB）は使わないことにしたため削除した（2026-10-05）

**水に入れないようにする壁（2026-10-05）**

* 水面（`Background/Landscape/Water`、高さy=−0.9）は平らな当たり判定を持つが、岸の地面が水面の下までなだらかに続いているため、そのままでは浅瀬に歩いて入れた
* シーンのルートに`WaterBlockers`を置き、岸に沿って見えない当たり判定の箱（`Blocker`、697個・高さ6m・`Water`レイヤー）を並べた。0.5m四方ごとに「水面以外の当たり判定の一番高い所が水面より低いか」を上から調べ、陸と接している水のマスにだけ壁を置いている
* 桟橋（`ModularWood_*`）・岩・ボートは当たり判定があるので「陸」扱い。桟橋の上は先端まで歩け、脇からは落ちない
* `Water`レイヤーはカメラの衝突判定（`Default`のみ）に含まれないので、カメラが見えない壁に押し戻されることはない
* **岸の地形・桟橋・水面の高さを変えたら壁の作り直しが必要**（作り直しはエディタでスクリプトを1回実行する方式で、手で並べたものではない）
