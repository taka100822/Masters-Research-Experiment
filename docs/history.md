## 2026-10-05 会話UIのデザイン

10.1 Phase 9「UI調整」の一部（2026-10-05 実装）。クエスト版のときに作ったので、説明・図に出てくるチェックリストは、今は残り時間の表示（3.5）に置き換わっている。MainSceneの会話まわりのUIを、村の世界観に合わせつつ「誰が話しているか／何を言っているか／何を選べるか／何キーで決定・送り・やめるか」が一目で分かるようにした。

### 改善前の問題（2026-10-05 Unity上で確認）

| # | 問題 |
|---|---|
| 1 | 選択肢パネルが右上のチェックリストに重なる（右下から上へ伸びるため） |
| 2 | 選ばれている選択肢が文字色（黄色）だけで分かりにくい。カーソルや下地がない |
| 3 | 名前と本文が同じ黒い窓の中で、同じ白・ほぼ同じ大きさ。誰の発言かが目立たない |
| 4 | 「次へ」の▼が窓の外（下）にあり、半透明で見落としやすい。操作キーの案内がどこにもない（会話中に「Enterで進む」「↑↓で選ぶ」が分からない） |
| 5 | 自由入力欄が画面中央に半透明で浮き、背景の村と重なって読みにくい。送信ボタンも白っぽく目立たない |
| 6 | 自由入力を**やめる手段がない**。「入力する」を選ぶと、何か送信するまで会話から抜けられない。空欄でも送信できる |
| 7 | 「Enterで話す」が画面右下の白文字だけで、明るい地面の上だと読めない。誰に話しかけるのかも分からない |
| 8 | Canvasが`Constant Pixel Size`。ビルドは全画面（1920×1080など）で動くので、UIが小さくなる（Gameビュー1069×601で作られている） |

### デザインの方針

* **村の建物から取る**：村は木組み（ハーフティンバー）の家・橙の屋根・白い漆喰壁。会話窓は**濃い樫材の板**、縁は**真鍮の細線**、文字は**漆喰の白**にする。いまの黒×銀の窓より村になじみ、明るい背景の上でも読める
* **印象に残すのは1か所だけ**：NPCの名前を、窓の左上の縁にかかる**吊り看板**（店の看板の形）にする。それ以外は静かにそろえる
* **条件差を作らない（1.4）**：「入力する」も他の選択肢と**同じ見た目**にする（アイコン・色分けをしない）。条件Bで増えるのは選択肢1行と、入力中の窓だけ
* 動きは「次へ」の▼が上下にゆっくり揺れるだけ（会話送りできることを知らせる）

**色**

| 名前 | 値 | 使う所 |
|---|---|---|
| 樫（窓の地） | `#2A1E16`・不透明度94% | 会話窓・選択肢・入力窓・話しかけ案内 |
| 梁（看板の地） | `#5A3A22` | 名前の吊り看板 |
| 真鍮（線・カーソル） | `#E0B354` | 窓の縁線・選択中のカーソル▶と下地（25%）・▼・操作案内のキー（`[Enter]`など） |
| 漆喰（本文） | `#F6EEDC` | 名前・本文・選択中の選択肢 |
| 煤（控えめな文字） | `#B9A88E` | 選ばれていない選択肢・操作案内・入力欄のプレースホルダー |

* 依頼人の金色（`clientColor`）・チェックリストの見出しの金色とは近い系統の色なので、画面全体の色がまとまる
* **文字**はいまの`NotoSansJP-Regular SDF`のまま（日本語フォントを増やさない）。大きさと太さで差をつける：名前26（TMPの太字）、本文24（行間+10%）、選択肢22、操作案内16（基準解像度1280×720のときの値）

**窓の素材**：白い角丸の板（`ui_panel_fill.png`）と、角丸の縁線（`ui_panel_frame.png`）を1枚ずつ作り（`Assets/Texture/`、9スライス）、`Image`の色で塗り分ける。購入アセットやいまの黒×銀の画像（`panel_rect_black-silver_03_128.png`）は変更しない。

### 画面構成（基準1280×720）

```text
                                                   ┌ミニマップ┐
                                                   └────────┘
                                                   ┌チェックリスト┐
                                                   └────────────┘
                                ┌──────────────────────┐
                                │▶ 何か知らない？        │ ← 選択肢（選択中は真鍮の下地＋▶）
                                │  なんでもない          │    窓の右寄り・中央より右300pxまで
                                │  入力する              │    （チェックリストと重ならない）
                                └──────────────────────┘
   ╔═══════════╗
   ║ 薬師ティム ║ ← 吊り看板（梁色＋真鍮の縁、窓の上辺にかかる）
 ┌─╨───────────╨──────────────────────────────────────────┐
 │  本文（24px、最大3行）                                    │
 │                                                        │
 │                              [↑][↓] 選ぶ  [Enter] 決定  ▼│ ← 操作案内＋▼
 └────────────────────────────────────────────────────────┘
```

* 会話窓：幅960×高さ170、画面下から24px。本文は左揃え、左右の余白36px
* 吊り看板（`NamePlate`）：窓の左上（左から28px）で、上辺をまたぐ位置に置く。幅は名前の長さに合わせて伸びる（`ContentSizeFitter`）
* 選択肢：画面下から230px（看板より上）、右端を画面中央+300pxにそろえる。行（`ChoiceRow1〜3`、下地の`Image`）の中に`Choice1〜3Text`があり、選択中の行だけ真鍮25%の下地＋先頭に▶。選ばれていない行は煤色で、▶の幅を透明であけて文の頭をそろえる。使わない行は非表示
* ▼（`NextIndicator`）は窓の中の右下で、`UIBob`で上下に4px揺れる。選択肢を選んでいる間は出さない

**操作案内**（`KeyGuideText`。窓の右下、状態ごとに`DialogueManager`が切り替える。キーは真鍮色の文字）

| 状態 | 案内 |
|---|---|
| `InDialogue` | `[Enter] 次へ`（`nextId=-1`のノードでは`[Enter] 閉じる`） |
| `InChoice` | `[↑][↓] 選ぶ　[Enter] 決定` |
| `InTyping` | `入力したら「送信」を押してください` |
| AIの返答待ち | `返事を待っています…` |

### 自由入力の窓

```text
 ┌──────────────────────────────────────────────────────────┐
 │ 薬師ティムに話しかける                                      │ ← 小見出し（InputHeaderText・煤色）
 │ ┌──────────────────────────────────┐ [ やめる ] [ 送信 ]   │ ← 入力欄（漆喰の地・濃い文字）
 │ │ 聞きたいことを書いてください       │                       │
 │ └──────────────────────────────────┘                       │
 └──────────────────────────────────────────────────────────┘
 ┌ 会話窓（直前のセリフはそのまま表示）─────────────────────────┐
```

* 会話窓の上（画面下から230px、看板にかからない位置）に、会話窓と同じ幅960×高さ104で出す（画面中央に浮かせない。チェックリストとも重ならない）
* **送信**（決定）：真鍮の地＋濃い文字。入力欄が空（空白だけを含む）の間は押せない
* **やめる**（キャンセル、`CancelButton`→`DialogueManager.OnClickCancelInput`）：枠線だけのボタン。入力欄を閉じ、同じノードの選択肢（「入力する」を含む）に戻る。書きかけの文章は捨てる（送れなかった文章の残し（4.6）も消す）
* プレースホルダーは「聞きたいことを書いてください」（NPCへの質問を書く場面なので）

### 話しかけ案内（`TalkHint`）

画面下中央（下から48px）に、樫色の小さな札で`[Enter] 薬師ティムと話す`と出す（近くのNPCの`displayName`を入れる）。`TalkHint`は札（`Image`）で、文字はその子の`TalkHintText`。会話窓が出ている間は出さない。

### 他のパネル

チェックリスト・ミニマップの枠・設定パネル（とそのボタン）も、窓の画像と色だけを同じものに差し替えた（配置・大きさ・中身は変えない）。終了画面は変えていない。

### Canvasの拡大縮小

`Canvas Scaler`は`Scale With Screen Size`（基準1280×720、幅と高さの中間 0.5）。全画面のどの解像度でも、UIが画面に対して同じ割合の大きさになる。ミニマップ・チェックリスト・設定パネルも一緒に拡大縮小される。

### 研究への影響（1.6）

| 変更 | 影響 | 判断 |
|---|---|---|
| 見た目・配置・操作案内 | 両条件・両セットで同じ。条件差は増えない | 問題なし |
| 自由入力の「やめる」 | 条件Bだけに関係。以前は一度「入力する」を選ぶと何か送るまで抜けられず、意図しない入力（空欄・試し打ち）がログに混ざりえた。やめられるようにしたので、`free_input_submit`は「本当に送った入力」だけになる | 会話方式の変更。2026-10-05 承認 |
| 空欄では送信できない | 空の`free_input_submit`とAI呼び出しがなくなる | 2026-10-05 承認 |
| ログ項目の追加 | `free_input_cancel`（自由入力をやめた：NPC ID・ノードID）を6.3に追加。summary.csvは変えない | ログ項目の変更。2026-10-05 承認 |

### 実装の構成

* `Assets/Texture/ui_panel_fill.png`・`ui_panel_frame.png`：エディタ上のコードで生成した64×64の白い角丸画像（9スライス、境界18px）
* `DialogueManager`：Inspectorの「Dialogue UI Style」に`keyGuideText`・`talkHintText`・`inputHeaderText`・`choiceRows`・`sendButton`（未設定でも動く）。操作案内の切り替え（`SetKeyGuide`）、選択肢の見た目（`UpdateChoiceUI`）、話しかけ案内の文、`OnClickCancelInput()`、送信ボタンの有効・無効（`UpdateSendButton`）
* `UIBob`：▼を上下に揺らす（`Time.unscaledTime`）
* `ExperimentLogger`は変更なし（知らないイベント名もそのまま書くため）

* 参加者が見る画面の見た目だけの変更で、両条件・両セットで同じ（1.4）

* ログ・実験設定の受け渡し（`ExperimentConfig`）は変えない

### 実装の構成

* `TitleMenuUI`：`cancelButton`（未設定でも動く）と`CancelDeveloperModal()`（値を変えずに閉じる）。設定表示の文は`UpdateSummary()`で`P000・A・S1`の形にする。`hideWhileModalOpen`は`TitleText`と`StartButton`
* `TitleScene.unity`：既存のGameObject名と`TitleMenuUI`の参照は残し、`SummaryPlate`・`CancelButton`と各窓の縁（`Frame`）を追加

## 2026-10-05 設定パネルのデザイン

設定パネル（3.6）を3.7・3.8と同じ見た目・操作の約束（真鍮の地＝決定、枠線だけ＝それ以外、`[キー]`は真鍮色）にそろえた（2026-10-05 実装）。大きさは基準1280×720のときの値。

### 改善前の問題（2026-10-05 Unity上で確認）

| # | 問題 |
|---|---|
| 1 | 窓の色は3.7で差し替えたが、スライダーがUnity標準（白い溝・黄色・白いつまみ）のままで浮いている |

## 2026-10-05 会話の本文の改行

10.1 Phase 9「UI調整」の一部（2026-10-05 実装）。下の例のセリフはクエスト版のもの。

### 問題（2026-10-05）

会話の本文（`DialogueText`）の改行位置がばらばらで読みにくい。TextMeshProは日本語を**1文字ごとにどこでも**折り返す（句読点の行頭禁止だけは守る）ので、窓の右端に来た文字で機械的に改行され、単語の途中で切れる。

```text
村に届く荷物は、いつも村の入り口に置かれるんだ。薬草の包
みもきっとあそこに置かれたはずだよ。
```

CSVのセリフに手で改行を入れても、AIの返答（条件B）は長さも内容も毎回違うので直せない。

### 方針：文節で折り返す

* 本文を**文節**（「薬草の」「包みも」「きっと」…）に区切り、**文節の途中では改行しない**ようにする。改行は文節と文節の間だけで起きる
* 区切りは**BudouX**（Googleの日本語改行用ライブラリ。Chromeの`word-break: auto-phrase`にも使われている。Apache 2.0）の日本語モデルを使う。辞書を持たない小さな学習済みモデル（JSON 1つ）で、C#に移すのは数十行
* CSVのセリフにもAIの返答にも、**表示の直前に同じ処理**をかける。会話データ・プロンプトは書き換えない

```text
村に届く荷物は、いつも村の入り口に置かれるんだ。薬草の
包みもきっとあそこに置かれたはずだよ。
```

**しくみ**：文節ごとに`<nobr>…</nobr>`（TMPの改行禁止タグ）で囲み、文節の間に幅ゼロの空白（U+200B）を入れて改行してよい位置にする。1つの文節が1行より長いとき（ほぼない）は、TMPがふつうに途中で折り返す。

* 対象：NPCのセリフ（`ShowNode`）とAIの返答（`ShowAIResponse`）。選択肢・名前・操作案内は短いので変えない
* `<`などTMPのタグと紛らわしい文字がAIの返答に入っていても壊れないよう、元の文のタグはそのまま残し、タグの中は区切らない
* 手で入れた改行（CSVの`\n`など）はそのまま残す

### 研究への影響（1.6）

| 変更 | 影響 | 判断 |
|---|---|---|
| 本文の改行位置 | 見た目だけ。両条件・両セットで同じ処理。文の中身は変わらない | 問題なし。2026-10-05 承認 |
| ログ | `npc_line`・`ai_response`には**区切る前の元の文**を書く（タグを混ぜない）。ログ項目は変えない | 問題なし |

### 実装の構成

* `Assets/Resources/BudouX/ja.json`：BudouXの日本語モデル（GitHub `google/budoux`から取得。ライセンス表記を同じフォルダに置く）
* `JapaneseLineBreaker`（新規・静的クラス）：`Format(string text)`で文節ごとに`<nobr>`で囲んだ文を返す。モデルは最初の1回だけ読む。読めなければ元の文をそのまま返す（今と同じ表示）
* `DialogueManager`：`dialogueText.text = ...`の2か所（`ShowNode`・`ShowAIResponse`）で`JapaneseLineBreaker.Format`を通す
* 確認（2026-10-05、Unity上で会話窓と同じ幅888px・24pxのTMPに表示）：会話データの全56行のうち折り返す12行すべてで、改行は文節の間だけで起きた（文節の途中での改行0件、行数は増えず最大2行）。`NotoSansJP-Regular SDF`はU+200Bを持つので□にならない
* BudouXの区切りが辞書の単語と合わないことはある（例：「すれ違った」が「すれ／違った」に分かれる）。そのときもその区切りの間で改行されるだけで、1文字ずつの折り返しよりは読みやすい

### 追加：入るなら文の終わり（「。」「！」「？」）の後で改行する（承認・実装済み）

文節で折り返すだけだと、1つの行に前の文の終わりと次の文の始まりが並び、文の区切りが目で追いにくい。窓に収まるときは、**文の終わりの後で改行**して1文ずつ行を分ける。

**決まり**

* 本文の途中にある文の終わり（`。！？!?`）の後ろを改行の候補にする。「！？」のように続くときはまとめて1つの終わりとし、直後に`」』）)`が続くときはその後ろ。本文の最後の終わりは候補にしない
* 前の候補から順に、そこで改行しても**本文が3行（窓に入る行数）以内に収まるときだけ**改行する。収まらない候補は飛ばす（文節での折り返しはそのまま）
* 行数はその場で`DialogueText`に並べて数える（窓の幅・文字の大きさを変えても正しく働く）。数えられないときは改行を足さない
* CSVのセリフにもAIの返答にも同じ決まりをかける。AIの返答がもともと3行を超えるときは改行を足さない

**全セリフに当てた結果**（Unity上、幅888px・24px）：途中に文の終わりがある39行（候補43か所）すべてで改行が入り、3行を超えたものはない。

```text
村に届く荷物は、いつも村の入り口に置かれるんだ。
薬草の包みもきっとあそこに置かれたはずだよ。

ありがとう！
村の人に聞いて回ってくれ。
何か分かったら知らせてほしい。

準備を始めたのは3日前だよ。
灯篭もその日に片付けたはずだけど、僕は飾りつけの係だったから、どこへ
運んだかは知らないんだ。
```

**研究への影響（1.6）**：見た目だけ。両条件・両セットで同じ決まり。文の中身・ログ（元の文を書く）は変わらない。

**実装の構成**

* `JapaneseLineBreaker`：`Format(string text, TMP_Text target, int maxLines)`を足す。文の終わりの候補ごとに改行を入れた文を`target.GetTextInfo`で数え、`maxLines`以内なら残す。最後に今の文節の処理をかけて返す
* `DialogueManager`：Inspectorに`maxDialogueLines`（初期値3）。本文を出す2か所で新しい`Format`を使う（パネルを表示してから数える）
* 確認（2026-10-05）：全セリフ56行のうち39行で文の終わりの後に改行が入り、3行を超えたもの・文節の途中での改行は0件。プレイモードの会話窓（`DialogueText`）でも同じく表示された
* 候補は前から順に使うので、文の多い長い返答（主にAI）では、前の文で行を使い切り、後ろの文どうしが同じ行に並ぶことがある（3行に収めるのを優先する）

## 2026-10-05 AIの返答が得られなかったとき

参加者が「壊れた」と感じたり、操作できなくなったりしないようにする。

**待っている間**
* 送信したら、会話ウィンドウのセリフを「……」にして、返答を待っていることが分かるようにする（今は直前のセリフが出たまま止まって見える）

**時間切れ**
* 今は問い合わせに制限時間が無く、通信が固まると参加者がずっと待たされて操作できなくなる。**20秒**で打ち切り、エラーとして扱う（`UnityWebRequest.timeout`）

**エラーのときの表示**
* 「エラー」の代わりに、世界観を壊さない一文をNPCのセリフ欄に出す：
  `（うまく伝わらなかったようだ。もう一度話しかけてみよう）`
  （かっこ書きのナレーションにして、NPC本人のセリフに見えないようにする。全NPC共通）
* エラーかどうかは、`ChatGPTClient.SendChatMessage`が返す`ChatResult`（`Success`／`Text`／`Error`）で判定する。「エラー」という文字列はもう返さない

**もう一度試す**
* エラーのあとEnterを押すと、これまでどおり同じノードの選択肢（「入力する」を含む）に戻る（5.3の`nextId`＝自分自身の仕組み）

**ログ**
* `ai_response`の`text`には参加者に表示した一文を、`detail`に失敗の理由を書く（`error=timeout`／`network`／`http_<コード>`／`parse`／`no_key`）。`is_error=1`は今までどおり

## 2026-10-29 1人2回の自動進行

今の仕様はREADME 2.5（進め方）・2.4（2回目の簡易版）・3.1（開発者用モーダル）・3.7（アンケート画面）。

### 問題

* 1人が2回遊ぶのに、2回目も1回目と同じチュートリアル（歩く・クリス・設定パネルまで）をやり直していて手間だった
* 1回ごとに実験者が開発者用モーダルで条件・話題セットを選んでいた。グループ（README 1.3）と違う組み合わせを選ぶ・2回目に切り替え忘れる、といった人為ミスが起きうる
* 時間切れのあとは「実験者の指示があるまでお待ちください」で止まり、2回目は実験者がタイトルからやり直していた

### 決めたこと

* 実験者は**参加者IDだけ**を入れる。グループは`(番号 − 1) を4で割った余り ＋ 1`（番号はIDの末尾の数字）で、実験手順書の前準備の割り振り（ID1→グループ1、ID2→グループ2、…、ID5→グループ1）と同じ
* 1回目のチュートリアル → 本番 → アンケート画面 → 2回目のチュートリアル → 本番 → アンケート画面 → おわりの画面、と続けて進める
* 2回目のチュートリアルは簡易版（話しかける → 新しい話し方 → Enter）。2回目は話し方が変わるので、話しかけと新しい話し方の練習は残し、歩き方・2人目との会話・設定パネルは省いた
  * 最初は「タイトルで選んだ条件・話題セットがグループの2回目と一致したら簡易版」としたが、自動進行にしたので「今が2回目なら」に単純にした（食い違いが起きないので、その警告も無くした）
* アンケートは外部のフォームで答える。ゲームは待つだけで回答を記録しない。進むのは参加者が「アンケート回答完了」→確認で「はい」を押したとき（間違って押してもすぐ進まないように確認を挟む）
* 参加者IDの初期値は`P000`から空にし、IDが無い間は「はじめる」を押せなくした（入れ忘れたまま始めるミスを防ぐ）
* やり直し用に、開発者用モーダルに「始める回」（1回目から／2回目から）を置いた

### 研究への影響

条件・話題セットの組み合わせと順番は今までと同じ（README 1.3）。変わるのは実験者の操作と、2回目のチュートリアルの長さ、アンケートを答える場面（ゲームの画面の上で待つ）だけ。実験手順書の「アンケート」「2回目の準備」の段取りは、この流れに合わせて直す必要がある。

### 確認したこと（2026-10-29）

* コンパイルエラー・警告なし。IDの番号→グループ→各回の条件・話題セットの計算を、P001〜P006・条件2つ・セット2つの全組み合わせで確かめた（P001・P005はB・S2、P002・P006はB・S1、P003はA・S2、P004はA・S1が2回目）
* Unity上でPlayし、P005で通して確かめた：タイトル（未設定の間は「はじめる」が灰色）→ モーダル（グループ1：1回目 A・S1／2回目 B・S2）→ 1回目のチュートリアル（通常版・A・S1）→ 本番 → アンケート画面 → 確認 →「はい」→ 2回目のチュートリアル（簡易版、2から始まる・B・S2）→ 本番 → アンケート画面 →「はい」→ おわりの画面。ログの`session_start`・`tutorial_start`に`round=`が入ることも確かめた
* 時間切れ・チュートリアルの完了は、コードから呼んで起こした（実際に5分待つ・会話をこなす確認はしていない）
* TutorialSceneはMainSceneを変えたので`TutorialSceneBuilder`で作り直した

### 決めたこと

* ログの書き込みは、AI接続（2026-10-30「実験当日の準備と小さな修正」）と同じく、開発者用モーダルを**開くたびに自動で**確かめる。保存先に短いファイルを書いてすぐ消す。失敗しても止めない
* 同じIDの本番のログがあれば、エラーの行に**注意として出すだけで止めない**。途中で落ちて「2回目から」やり直すときは、1回目のログがあるのが正しいため。大文字・小文字は区別せず（打ち間違いを拾うため）、`P1`と`P10`は取り違えないよう、IDの後ろの`_`まで比べる
* アンケート画面に「アンケートを開く」を足し、Googleフォームの**事前入力URL**でプレイヤーIDと回を入れて開く。条件・話題セットは参加者の目に入るので入れない。押す順に左から並べ、最初に押す「アンケートを開く」を真鍮の地（主な操作）、「アンケート回答完了」を枠線だけにした。画面の文も「開いて答え、戻って回答完了を押す」の順に変えた
* フォームの欄の番号（`entry.`）は、公開されているフォームの中身から読んだ（「プレイヤーID」＝`entry.1776098365`、「何回目のプレイですか？」＝`entry.1533040520`）
* Player Settingsの「Force Single Instance」をオンにし、2つ目は起動しないようにした

### 研究への影響

* 参加者が遊ぶ内容・ログ項目・アンケートの質問は変えていない。アンケートは、IDと回を自分で入れる手間が無くなるだけ
* 試しに書くファイルはすぐ消し、ログ・summary.csvには何も足さない。注意の表示・「アンケートを開く」を押したことはログに書かない

### 確認したこと（2026-10-30）

* コンパイルエラー・警告なし
* フォームの事前入力URL（`P999`・`2回目`）をブラウザで開き、2つの欄が入った状態で開くことを確かめた（送信はしていない）。フォームはログイン不要で、メールアドレスも集めていない
* TitleSceneをPlayしてモーダルを開き、`ログ保存 OK`と出た。IDを`P000`→27件、`P100`→1件（チュートリアルの1件は数えない）、`p100`→1件、`P10`・`P1`・`P999`・空→注意なし、になることを確かめた。モーダルの見た目（窓640×640、行が重ならない）も画面で見た
* MainSceneで時間切れの画面を出し、「アンケートを開く」（真鍮の地）と「アンケート回答完了」（枠線だけ）が並び、新しい文が収まることを画面で見た
* `forceSingleInstance`が`1`になったことをProjectSettingsの差分で確かめた
* 次は試していない：書き込めないときの表示、エディタから「アンケートを開く」を押してブラウザが開くこと、**ビルド版で全画面のゲームの上にブラウザが前に出て、答えたあとゲームに戻れること**（実験に使うPCで確かめる）、2つ目の起動が止まること
* TutorialSceneは作り直していない。アンケート画面はチュートリアルでは出ず、`openFormButton`が未設定なら何もしないため

## 2026-10-30 集計の行を失わない・どのビルドで遊んだかを残す

今の仕様はREADME 6.7（summary.csvに書けないとき）・3.1（ログ保存の表示）・6.3（ビルドの記録）・7.7。

### 問題

* **summary.csvの行が黙って消える**。参加者と参加者のあいだに実験者が`summary.csv`をExcelで開いたままにすると、Excelがファイルをロックし、次のセッションの終わりに集計の行を書けない。`ExperimentLogger`はConsoleにエラーを出すだけで、ビルド版では気づけない（イベントのログは残るので計算し直せるが、気づかなければ集計が欠けたまま分析してしまう）

## 2026-10-30 実験後アンケート：理由を質問ごとに聞く

Googleフォーム「実験後アンケート」（ゲームの外。2回目のあとに答える）の、セクション2「2つの話し方の比較」を直した。ゲーム・ログ・「ゲーム体験アンケート」は変えていない。

### 問題

* 5つの比較の質問（楽しかった／村人と本当に会話している感じがした／もっと村人と話したいと思った／話しやすかった／もう一度遊ぶならどちら）の理由を、最後の**1つの欄でまとめて**聞いていた（「上の5つの質問の答えについて、理由を自由に書いてください。」・必須）
* 1つの欄だと1〜2問分しか書かれなかったり、どの答えの理由か分からなくなったりする。必須なので「特になし」のような答えも増えやすい

### 決めたこと

* 5つの質問それぞれの**すぐ下**に理由の欄を置く（全部で5つ）。まとめの欄は、5問目の理由の欄に書き換えた
* 5つとも同じ形：
  * 質問文「そう答えた理由を教えてください（任意）」
  * 説明「どの場面でそう感じたかも書いてもらえると助かります。」
  * 形式は段落、**必須にしない**
* どの欄も同じ文にしたのは、すぐ上の質問の理由だとそのまま伝わり、回答を並べたときも見分けやすいため

### 研究への影響

* 比較の5問そのもの（文・選択肢・必須）は変えていない。理由の欄は増えたが任意なので、答える人の負担はほとんど増えない
* 回答のスプレッドシートは列の並びが変わる（本番の前の変更なので、分析への影響は無い）

### 確認したこと（2026-10-30）

* フォームの編集画面で、セクション2が「質問→理由の欄」の順に5組並び、理由の欄に必須の印が無いことを確かめた。変更はドライブに保存された
* 参加者の画面（プレビュー）での見た目と、送信は試していない

## 2026-10-30 クリスに先に話しかけられないようにする

チュートリアル（README 2.4）で、旅人クリス（`TUT002`）には4の札が出るまで話しかけられないようにした。

### 問題

クリスはケビンの奥（右5m・前11m）に立っていて、1〜3の間でも話しかけられた。歩く練習のついでや、地図の白い丸を見てクリスに先に話しかける参加者がいた。そうすると、

* 2の間：クリスとの会話が始まっても「話しかけた」にならず、札はケビンのまま。「話しかけたのに進まない」と迷う
* 3の間：クリスとの会話を最後まで進めても3は終わらない
* 4になったら、もう一度クリスと話し直すことになる
* 2回目の簡易版（2 → 3 → 6）ではクリスの出番がないのに話せてしまう
* 条件Bでは、AIと話す回数が人によって増える（「その回の話し方を1〜2回練習する」でそろえた前提が崩れる）

### 決めたこと

* 4より前にクリスに近づくと、話しかけ案内の札（README 3.3）は`[Enter] 旅人クリスと話す`の代わりに`先に案内人ケビンと話しましょう`を出す。Enterを押しても会話は始まらない
* 4より前は、次に話す相手がいつもケビンなので、札の文はどの時点でも合っている（簡易版は3が終わると6で札ごと消える）
* 頭上の吹き出し・名前・地図の白い丸は残す。2の札「右上の地図の白い丸が村人です」で2人とも見せたいので、クリスを4まで隠す形にはしなかった（隠すと地図の丸の数が途中で変わり、ミニマップがNPCの一覧を最初に作る作りも直す必要がある）
* ケビンは今のまま（1の間でも話せる）
* 話しかけられなかったことはログに書かない

### 研究への影響

* チュートリアルで話す相手と回数がそろう。条件Bで本番前にAIと話すのは「ケビン＋クリス」まで、簡易版はケビンだけになる
* 本番（MainScene）には`TutorialGuide`が無いので、何も変わらない。ログの項目も変えない

### 確認

* コンパイルが通り、Consoleにエラーが出ないことを確かめた
* TutorialSceneをPlayし、クリスの前で札が1〜3のときは`先に案内人ケビンと話しましょう`（1行、札の幅は文に合わせて伸びる）、4・5のときは`[Enter] 旅人クリスと話す`になることを確かめた
* Enterで会話が始まらないことは、Game画面にフォーカスが無くスクリプトからのEnterが届かなかったため、Unity MCPでは確かめられていない

## 2026-10-30 「タイトルへ戻る」を開発者用コマンドにする

設定パネル（README 3.8）の「タイトルへ戻る」ボタンと、その確認を外した。代わりに、実験者だけが`Ctrl+Shift+T`でタイトルへ戻せる（README 2.5）。

### 問題

* 「タイトルへ戻る」は確認を付けても参加者の目に入る。押すと進み具合が消え、その回をチュートリアルからやり直すことになる
* 参加者がタイトルへ戻る理由は無い。戻したいのは、やり直しや動作確認をするときの実験者だけ
* アンケート画面・おわりの画面では設定パネルが開けないので、そこからは戻れなかった

* 設定パネルからボタンと確認（`TitleButton`・`ConfirmGroup`）を消す。パネルは「初期位置に戻る」と「閉じる」だけになる
* `Ctrl+Shift+T`で、確認なしでTitleSceneへ戻る。TutorialScene・MainSceneの**どの状態でも**効く（説明画面・会話中・自由入力中・設定パネル表示中・アンケート画面・おわりの画面）
* 画面のどこにも書かない。3つ同時押しなので参加者が誤って押すことはまず無く、確認も付けない
* 処理は以前のボタンと同じ（`back_to_title`でログを閉じる→`Time.timeScale = 1`→TitleScene。参加者ID・回は残る）

### 研究への影響

* 両条件・両セットで同じ。ログの項目は変えない（`session_end`の`back_to_title`は、書く場所がボタンからコマンドに変わっただけ）
* 参加者が誤ってタイトルへ戻り、セッションが途中で切れることが無くなる
* チュートリアルの5の札（設定パネル）は「初期位置に戻る」にしか触れていないので、文は変えない

### 確認したこと（2026-10-30）

* コンパイルが通り、MainScene・TutorialSceneから`TitleButton`・設定パネルの`ConfirmGroup`が消えたことを確かめた（TutorialSceneはMainSceneから作り直した）
* 実験者がPlayして、`Ctrl+Shift+T`でタイトルへ戻れることを確かめた
